/add-dir, /context, /compact: the three commands that keep a session alive

TL;DR

What they areThree session commands that attack the same problem from different angles: file scope (/add-dir), visibility into what fills the context window (/context), and freeing space without losing the work (/compact).

WhyLong sessions and work spread across more than one repository fill the context window and bump into the working directory. Without these three commands, the usual way out is opening a new session — and throwing away everything already investigated.

The priceEach has its own catch: file access is not loaded context, a summary is not the literal history, and /context only helps if someone remembers to run it.

01/add-dir

A session does not have to stay pinned to one directory.

By default, Claude only reads and writes inside the directory where the session was opened. That is a sensible safety fence — but a lot of real work does not respect it. The cause of a frontend bug can live in the response the backend returns; a function signature can be defined in a package that lives in another repository.

/add-dir <path> fixes that without leaving the session: you point at another directory's path, and from then on Claude has file access to both — where you started and what you just added. You can add more than one, and it lasts for the life of the session; if the same pair of repositories keeps coming up, promote it to permissions.additionalDirectories in the project's settings.json.

Without the command, the most common alternative is a second terminal pointed at the other repository. It works, but it costs more than it looks: the new session does not know what the first one already figured out. /add-dir keeps everything on one track — same conversation, same reasoning, both sides of the problem at hand.

A detail that tricks people: it is file access, not context. If the added repository has its own CLAUDE.md with conventions or skills, none of that loads on its own — worth making a habit of asking to read it before actually editing inside.

02/context

Before deciding what to do with the context window, see what is in it.

Every session has a context limit — and what fills it is not just the conversation. System prompt, tool schemas and connected MCP servers, files already read, the message history: all of it competes for the same space, and not always in the proportions you would guess.

/context shows the picture: how much each category is using, in numbers. It is the command that turns "I think the session is filling up" into a concrete datapoint — sometimes the villain is a handful of MCP servers with large schemas, not the conversation itself.

The value of /context is not acting on its own — it is informing the next decision. If the big slice is old conversation that no longer serves, it is time for /compact. If it is tools/MCP, maybe worth disconnecting something unused in this session. Without looking, the decision becomes a guess.

03/compact

Freeing space should not mean losing what was already investigated.

Long sessions pile up tool output, read files, discarded attempts — things that already did their job and do not need to sit there word by word, taking space. Without a way to clean that, when the session "fills up" the common path is opening a new one — and re-explaining everything from zero.

/compact is the middle ground: it summarizes the conversation so far, freeing space while keeping continuity — decisions made, hypotheses discarded, where the work stopped. You stay in the same session, just with more room ahead.

A summary is not the literal history.

/compact is summarization, not archival. What survives is the essence — the what and the why — not necessarily every textual detail, like an exact line number or the exact quote of a passage. If some detail is truly irreplaceable for what comes next, write it down (in a file, or explicitly in the conversation) before compacting — do not trust the summary to carry it on its own.

What none of the three solves alone

They buy space and reach. They do not replace judgment.

01

/context is a snapshot, not an alarm

It does not warn on its own when the window is filling up — someone has to remember to run the command.

02

/compact is controlled loss, not free loss

Every summary throws away detail. The right question is not "when to compact" but "what do I need to write down before compacting".

03

/add-dir is file scope, not imported conventions

The added repository still has its own rules, and they only apply if someone goes and reads them.

All three solve the same kind of friction: the temptation to abandon the session and start over because it got "too big" or "in the wrong repository". In practice, you can almost always continue where you stopped — you just have to know the command exists.
