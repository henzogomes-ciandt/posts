Stacked PRs: the open PR is the base for the next one

TL;DR

What it isThe next PR branches off the previous PR's branch, still open, and points at it instead of main. Each one shows only its own diff.

WhyYou stop waiting for a merge to keep going, and the reviewer gets pieces with a single subject inside.

The priceMerge bottom-up, never squash, and every PR green on its own.

The concept

Your PR's base does not have to be main.

A stacked PR is a PR whose base is the branch of another PR that is still open. It is literally just that. You do not wait for the first one to merge; you treat its branch as if it were already the base.

The second PR shows only its own diff. What the first one already contained does not appear again, because Git compares against the base you chose, not against main.

From there it becomes a chain: A comes off main, B off A, C off B. Each link is reviewable on its own, and merges happen bottom-up, in the order approvals arrive.

"Stacked PRs". I keep it in English, it is how everyone calls it.

How it works in practice

There is no new tool. Same git as always.

The only thing that changes is where the branch comes from and where the PR points.

# the first one, the way you already do it
git switch -c feat/a main
# work, commit, push
# open the PR:  feat/a  →  main

# the second one, without waiting for the first merge
git switch -c feat/b feat/a          # the base is the open PR's branch
# work, commit, push
# open the PR:  feat/b  →  feat/a    # the target too

What the reviewer sees in feat/b's PR is only what you did in B. That is not cosmetic: without the right target, the second PR would show A + B together and there would be no gain.

When A is approved and merged, you do two things with B — point the PR at main and bring main onto the branch.

git switch feat/b
git rebase --onto main feat/a feat/b
git push --force-with-lease

On GitHub the child retarget is automatic when the parent merges. On ADO it is not: it refuses to delete a branch that is still the target of another PR, so the delete that would trigger the retarget never happens and you switch the target by hand. I found that out the hard way, with a large chain already built.

Why this beats waiting

The point is not speed, it is decoupling.

Review is async and will stay that way. The reviewer has their own day, and sometimes their day is one meeting after another. What you get to choose is whether your work stays pinned to that calendar.

With the stack, the open PR stops being a stop and becomes a starting point. You move to the next part; A's review happens while B is being written; A's comments arrive whenever they arrive, and you fix them on A's branch and cascade forward.

There is a second effect I came to like as much as the first. Since opening one more PR costs nothing, you stop cutting work by size and start cutting it by type of review. One PR with just the component extraction, another with just the behavior change. The first the reviewer approves in five minutes and knows it is safe. The second they read slowly, which is what it deserves. Merge the two into one PR and they read both in the same mode, usually the fast one.

The rule you cannot loosen

Every PR in the stack needs to be green on its own.

Green on its own, not green on top of the stack.

If you stack on top of a branch that was never proven green by itself, you lose what stacking did best: when a test breaks three PRs up, you no longer know which link holds the problem. It happened to me in the middle of a chain, and finding out cost more than running everything beforehand.

What you pay for it

There is a price. It is low, but it is there.

01

A stale chain depreciates

The main moves. The longer the stack stays open, the more rebasing you do.

02

A late commit below conflicts with everything above

If a review tweak needs to land in a lower link, cascade it forward right away. Leaving it for merge day multiplies the conflict across the rest of the stack.

03

The merge order is not negotiable

Bottom-up, always.

04

Never squash a stack

Squashing rewrites the parent's commits into a new SHA and orphans every child. no-fast-forward and done.

05

A too-deep chain is a sign of something else

If you are on the eighth link, the problem is probably not the technique — it is that nobody is reviewing.

Stacked PRs do not make review faster. They take review off the critical path, which is different. If you have ever stared at an open PR with no idea what to do with your life until it merges, try it next time: branch off the open PR and keep going.
