Stacked PRs: o PR aberto já serve de base pro próximo

TL;DR

O que éO próximo PR sai da branch do PR anterior, ainda aberto, e aponta pra ela em vez da main. Cada um mostra só o próprio diff.

Por quêVocê para de esperar merge pra continuar, e o revisor recebe pedaços com um assunto só dentro.

O preçoMerge de baixo pra cima, nunca squash, e todo PR verde sozinho.

O conceito

A base do seu PR não precisa ser a main.

Uma stacked PR é um PR cuja base é a branch de outro PR que ainda está aberto. É literalmente só isso. Você não espera o merge do primeiro, você trata a branch dele como se já fosse a base.

O segundo PR mostra apenas o diff dele. O que o primeiro já continha não aparece de novo, porque o Git compara contra a base que você escolheu, não contra a main.

A partir daí vira uma corrente: A sai da main, B sai de A, C sai de B. Cada elo é revisável sozinho, e o merge acontece de baixo pra cima, na ordem em que as aprovações chegam.

“Stacked PRs”, ou PRs empilhados. Eu mantenho em inglês, que é como todo mundo chama.

Como funciona na prática

Não tem ferramenta nova. É o mesmo git de sempre.

A única coisa que muda é de onde a branch sai e para onde o PR aponta.

# o primeiro, como você já faz
git switch -c feat/a main
# trabalha, commita, push
# abre o PR:  feat/a  →  main

# o segundo, sem esperar o merge do primeiro
git switch -c feat/b feat/a          # a base é a branch do PR aberto
# trabalha, commita, push
# abre o PR:  feat/b  →  feat/a    # o target também

O que o revisor vê no PR de feat/b é só o que você fez em B. Isso não é detalhe cosmético: sem o target certo, o segundo PR mostraria A + B juntos e não teria ganho nenhum.

Quando A é aprovado e mergeado, você faz duas coisas com B — aponta o PR pra main e traz a main pra branch.

git switch feat/b
git rebase --onto main feat/a feat/b
git push --force-with-lease

No GitHub o retarget do filho é automático quando o pai mergeia. No ADO não: ele se recusa a deletar uma branch que ainda é alvo de outro PR, então o delete que dispararia o retarget nunca acontece e você troca o target na mão. Descobri isso do jeito difícil, com uma cadeia grande já montada.

Por que isso é melhor que esperar

O ponto não é velocidade, é desacoplamento.

O review é assíncrono e vai continuar sendo. O revisor tem o dia dele, e às vezes o dia dele é uma reunião atrás da outra. O que dá pra escolher é se o seu trabalho fica preso a esse calendário.

Com a pilha, o PR aberto para de ser uma parada e vira um ponto de partida. Você segue pra próxima parte; a revisão de A acontece enquanto B é escrito; os comentários de A chegam quando chegam, e você conserta na branch de A e cascateia pra frente.

Tem um segundo efeito que eu passei a gostar tanto quanto o primeiro. Como abrir mais um PR não custa nada, você para de cortar o trabalho por tamanho e passa a cortar por tipo de review. Um PR só com a extração de componente, outro só com a mudança de comportamento. O primeiro o revisor aprova em cinco minutos e sabe que está seguro. O segundo ele lê devagar, que é o que merece. Junte os dois num PR só e ele lê os dois no mesmo modo, geralmente o rápido.

A regra que não dá pra afrouxar

Todo PR da pilha precisa estar verde sozinho.

Verde sozinho, não verde no topo da pilha.

Se você empilha em cima de uma branch que nunca foi provada verde por conta própria, perde o que o stacking tinha de melhor: quando o teste quebra três PRs acima, você não sabe mais em qual elo está o problema. Aconteceu comigo no meio de uma cadeia, e o custo de descobrir foi maior que o de ter rodado tudo antes.

O que você paga por isso

Tem preço. É baixo, mas tem.

01

Cadeia parada se deprecia

A main anda. Quanto mais tempo a pilha fica aberta, mais rebase você faz.

02

Commit tardio embaixo conflita com tudo acima

Se um ajuste de review precisa entrar num elo de baixo, cascateie pra frente na hora. Deixar pro dia do merge multiplica o conflito por todo o resto da pilha.

03

A ordem de merge não é negociável

De baixo pra cima, sempre.

04

Nunca faça squash numa pilha

O squash reescreve os commits do pai num SHA novo e órfã todos os filhos. no-fast-forward e pronto.

05

Cadeia muito profunda é sinal de outra coisa

Se você está no oitavo elo, provavelmente o problema não é a técnica, é que ninguém está revisando.

Stacked PRs não deixam o review mais rápido. Elas tiram o review do caminho crítico, que é diferente. Se você já se pegou olhando pra um PR aberto sem saber o que fazer da vida até ele mergear, tenta na próxima: sai da branch do PR aberto e segue.
